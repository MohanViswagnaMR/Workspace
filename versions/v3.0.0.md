# v3.0.0 — Plugins, the Code layout & the guided workspace wizard (2026-07-19)

The biggest release so far: Workspace becomes **extensible like an editor**.
Plugins are plain folders of files with a typed manifest, a community
**plugin registry** indexes them straight from their authors' GitHub repos,
and Developer mode gets a faithful **VS Code-style Code layout**. Creating a
workspace is now a guided popup wizard, and the whole `src/` tree was
restructured into feature folders. Existing workspaces work as-is — every
new frontmatter field and folder is additive.

## Plugins — extend it like an editor

- **Plugin system** — a plugin is a folder at `plugins/<id>/` inside the
  workspace: `manifest.json` plus JSX (transpiled in the browser) or CSS.
  Nothing runs until you review and enable it; consent is remembered per
  **content hash**, so any file change asks again.
- **Typed plugins** (`src/services/plugin.js`, append-only registry):
  **`page`** — custom page types & file handlers; **`theme`** — CSS-only
  skins applied workspace-wide while enabled (built-in **Sepia Theme**
  sample). `layout`, `icons`, `syntax` and `components` are declared as
  *planned*, so older versions reject them with a clear message.
- **Permissions** — plugins declare every app service they use
  (`pages:read`, `pages:navigate`); the consent screen lists them and each
  one can be revoked in Settings → Plugins (`docs/PERMISSIONS.md`).
- **Uninstall** — removes `plugins/<id>/` from disk or Drive, forgets
  consent + grants, and restores any built-in the plugin was overriding.
- **Built-ins** — Habit Tracker (sample page plugin), **Coder Page** (the
  IDE-style editor, now the code-file handler for *both* layouts) and the
  Sepia Theme. The old Code Viewer sample was retired in Coder Page's favour.
- **File handlers** — Settings → File handlers offers, per extension and
  per layout, only page plugins that actually declare that extension;
  `name-(plugin-id).ext` still binds any plugin per file.

## The plugin registry & store

- **Community registry** — a separate repo
  ([workspace-plugin-registry](https://github.com/MohanViswagnaMR/workspace-plugin-registry))
  indexes plugins **by link only**: authors submit their repo via an issue
  form, GitHub Actions run the same compatibility checks the app runs, and
  passing plugins are indexed **pinned to the tested commit** — pushing new
  code never changes what users install until it is re-tested (weekly).
- **Plugin Store** — a new site page (navbar → Plugins, next to Docs) with
  an app-store gallery of built-ins + registry plugins, search, and a
  "Submit your plugin" flow. Installs pull from the author's repo at the
  pinned commit into the workspace's own `plugins/` folder.

## The Code layout (Developer mode)

- **VS Code anatomy** — title bar (brand, File/Edit/View/Go/Terminal/Help
  menus, search pill, Home ⟷ Code toggle), activity bar, EXPLORER with an
  OPEN EDITORS section (hover a row and its icon becomes the close ×),
  breadcrumbs, and a slim theme-tinted status bar.
- **Real terminal** — an xterm.js client for the local Docker bridge
  (`docker/terminal-bridge`); the bottom panel has PROBLEMS / OUTPUT /
  TERMINAL tabs, survives tab switches, and **never auto-opens** — it
  returns only if it was open last time (Ctrl+` toggles).
- **Extensions view** — the activity-bar plug icon opens a VS Code-style
  panel: INSTALLED with Enable/Disable/Apply actions, MARKETPLACE with
  one-click installs from the registry, and a full extension detail page.
- **Trash view**, right-click menus on tabs (Close / Close Others / Close
  All) and explorer rows (Open / New Page inside / New Folder / Delete),
  and a Close-workspace button in the activity bar.
- **"smart page" switch** (status bar) — flip any smart page between the
  block editor and its **raw on-disk `.md`** (frontmatter included); edits
  round-trip through the same parser the disk loader uses.
- Picking the **Code layout in the wizard** opens the workspace directly in
  it; the Home ⟷ Code switch lives in the title bar.

## Creating & connecting workspaces

- **Two-button start** — *Create workspace* and *Connect* (matching accent
  tiles) open a centered **popup wizard** with numbered, labeled steps:
  **Name → Layout (Home/Code) → Theme (live accents) → Plugins → Starter
  pages → Storage**. Completed steps are clickable; tall steps scroll
  inside the dialog.
- The **Plugins step** searches built-ins + the registry and connects any
  GitHub plugin link; chosen plugins are installed and pre-enabled in the
  new workspace. The **Starter pages** step seeds optional pages
  (Getting Started, Tasks, Meeting Notes, Reading List).
- Simple **markdown pages** (`kind: md`) — name a new page `notes.md` for a
  raw-markdown page; `hello.py` creates a file page; name-first creation
  decides the kind everywhere (sidebar, wizard, terminal, File menu).

## Chrome & polish

- **Welcome page redesigned** — "New in v3" badge, a CSS-drawn product
  shot, an 8-card feature grid covering the v3 features, an "Extend it
  like an editor" plugin spotlight and the updated on-disk tree.
- **Rose** is the new default accent (violet stays available).
- **Shared UI components** — `Button`/`TileButton`, `Brand` (the ◧ chip),
  `SavePill` (the ✓ Saved pill, now identical in both layouts) and
  `CustomSelect` live in `src/components/ui/`.
- "Manage workspaces" left the start navbar (unlink/manage still available
  in-app); the plugin icon is a plug 🔌 everywhere.

## Under the hood

- **`src/` restructure** — feature folders with a one-way import flow:
  `lib/` → `services/` → `components/` → `views/` → `layouts/` →
  `workspace.jsx`/`pages/`; storage backends live in `src/storage/`.
  `workspace.jsx` shrank from ~4,200 to ~2,600 lines.
- Verified end-to-end by a headless Chrome (CDP) suite covering the wizard,
  store, editors, menus, theme plugins, extensions view and both layouts.
- Service-worker cache name bumped (`workspace-v3.0.0`) so installed PWAs
  pick up the new shell after all tabs close.
